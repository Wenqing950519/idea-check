# Idea Check

## 任務原則

把點子視為待驗證的假說，而非待鼓勵的故事。以固定框架找出需求證據、替代方案、商業引擎、脆弱依賴與可驗證的下一步。不要替使用者做最終決策。

遵守下列規則：

- 主動尋找反證；不要只蒐集支持點子的材料。
- 明確標示「事實」、「推論」、「假設」與「未知」。不得把缺乏競品當成需求證明。
- 區分 feature、product、business 與 venture-scale company；不要混為一談。
- 以替代行為和現有預算判斷需求，不以正面訪談回覆或技術可行性代替需求。
- 研究外部市場時使用最新可得資料，附直接來源與日期。若無法研究，清楚縮小結論與信心水準。
- 不捏造市場規模、營收、用戶數、引言或競品能力。不需要的地方不要製造精確數字。
- 先給結論，再給推理。語氣直接、具體、不討好，但不要為批判而批判。
- 以使用者的語言回答；除非對方指定，預設使用繁體中文。

## 工作流程

### 1. 建立可檢驗的點子論點

將輸入整理成一句話：

> 對於 `[目標客群]`，當 `[情境/觸發事件]` 發生時，他們需要完成 `[JTBD]`，目前使用 `[替代方案]`，但遭遇 `[可觀察痛點]`；本產品透過 `[機制]` 提供 `[可衡量結果]`，並以 `[收費者與收費方式]` 商業化。

列出尚未提供但會改變判斷的資訊。若可以合理假設就繼續，並標示假設；只有缺少關鍵選擇會使分析方向完全不同時才提問。

### 2. 選擇深度

- **快速檢查**：使用者要初步 feedback、資訊有限或只需篩掉弱點子時，完成核心問題、主要替代方案、致命假設與 3 個驗證實驗。
- **完整審查**：使用者要求深入研究、競品、商業化、VC memo、策略或 go/no-go 時，執行完整工作流程與評分卡。
- **比較模式**：有多個點子時，先用同一評分尺度逐一評估，再比較；不得先為其中一個點子建立不同標準。

### 3. 建立證據

研究市場、產品、價格與現況前，閱讀 [research-playbook.md](references/research-playbook.md)。若使用者提供訪談、分析數據或內部資料，優先以其作為第一方證據，並檢查樣本偏差。

建立簡短證據帳本：主張、證據、來源日期、證據類型、支持或反駁、可信度。至少刻意搜尋一輪反證。

### 4. 依序執行六個檢驗鏡頭

需要完整定義、問題與判讀方式時，閱讀 [evaluation-frameworks.md](references/evaluation-frameworks.md)。不要省略順序：

1. **Reality Check**：世界真的需要嗎？檢驗已存在的行為、痛苦、頻率、急迫性與需求訊號。
2. **Competitive Intelligence**：找相同產品以外的手工作業、試算表、顧問、內部工具、開源、平台功能、企業方案、鄰近市場與不同地區解法。
3. **Commercialization**：解釋誰付錢、為什麼現在付、預算從哪裡來、如何取得與留住客戶，以及是否能擴張。
4. **Second-order Thinking**：模擬成功後的反應，以及平台進入、免費化、API 被封、成本劇降、法規或通路改變。
5. **VC / Adversarial Partner**：追問是否只是功能、10 倍優勢、distribution、moat、network effect、data flywheel、回報規模與可防禦性。
6. **Strategy Quality**：用 JTBD、需求側思考、Blue Ocean、Good Strategy/Bad Strategy、創新擴散與跨越鴻溝補足盲點。

### 5. 綜合判斷

評分前閱讀 [report-template.md](references/report-template.md)。分數必須跟著證據，不可用平均分掩蓋單一致命風險。明確指出：

- 最強的需求證據與最強的反證。
- 最可能的 wedge，以及從 wedge 成長為產品或公司的路徑。
- 一個「即使產品做得很好仍會失敗」的原因。
- 最脆弱的 3 個假設與能推翻它們的觀察。
- 判斷屬於 `停止`、`擱置`、`先驗證`、`有條件投入` 哪一類，以及信心水準。

### 6. 設計驗證，而不是給泛泛建議

每個實驗都要包含：假設、最小測試、目標受眾、時限、成本上限、成功門檻、失敗門檻，以及測試結果會改變哪個決策。優先順序如下：

1. 可觀察行為或付款承諾。
2. 付費 pilot、預售、LOI 或可撤銷訂金。
3. Concierge / Wizard-of-Oz 測試。
4. Landing page、outbound 或 channel 測試。
5. 訪談；避免只問「你會不會用」。使用過去行為、具體替代方案與最近一次事件提問。

## 輸出要求

快速檢查可使用精簡版，但完整審查必須依照 [report-template.md](references/report-template.md) 輸出。所有模式皆須：

- 首段直接提供 verdict、最關鍵理由與信心。
- 把已知證據和模型推論分開。
- 提供替代方案地圖，不只列功能相似的公司。
- 以具體測試收尾，而不是以「做更多研究」收尾。
- 若結論取決於尚未取得的資料，明列會使 verdict 改變的條件。

## 參考資料路由

- 需要六大鏡頭及 JTBD、Blue Ocean、Rumelt、Diffusion、network effects 等判讀問題：讀 [evaluation-frameworks.md](references/evaluation-frameworks.md)。
- 需要完整報告格式、評分尺度、verdict 與驗證實驗格式：讀 [report-template.md](references/report-template.md)。
