# Evaluation Frameworks

## 目錄

1. Idea Reality Check

## 1. Idea Reality Check

核心問題是「世界真的需要嗎？」而不是「有沒有人做過？」

依序檢查：

- **Customer**：最窄且可接觸的首批客群是誰？使用者、受益者、決策者與付費者是否相同？
- **Trigger**：什麼具體事件讓他們今天開始解決，而不是明年？
- **JTBD**：他們試圖取得什麼進展？功能只是手段，理想結果是什麼？
- **Pain**：現況造成時間、金錢、風險、收入損失或情緒成本中的哪一種？
- **Frequency**：問題發生與產品價值被感知的頻率為何？
- **Consequence**：延後六個月的代價是什麼？若幾乎沒有代價，急迫性可能不足。
- **Existing behavior**：他們現在實際如何處理？已投入什麼資源？
- **Pull**：是否出現主動搜尋、轉介、反覆使用、提供資料、試用投入或付款承諾？
- **Why now**：技術、法規、成本、通路或行為改變，是否讓今天成為合理時機？

強證據由高至低通常為：付款/續約、持續使用、不可逆承諾、可觀察 workaround、最近一次具體行為、表達的偏好。不要用「受訪者說會用」取代行為證據。

檢查 The Mom Test 風格的訪談品質：詢問最近一次、現行流程、已花成本、嘗試過什麼與誰批准預算；避免介紹點子後尋求稱讚。

## 2. Competitive Intelligence

先定義競爭單位：客戶要完成的工作、使用情境、預算與替代行為。再建立替代方案地圖：

| 類別 | 要回答的問題 |
|---|---|
| 直接產品 | 同一客群、同一工作、相似產品如何定位與收費？ |
| 間接產品 | 哪些相鄰工具可用不同方式完成工作？ |
| 手動/服務 | 試算表、人員、顧問、代理商如何解決？ |
| 內部建置 | 大客戶是否偏好自行開發？原因是控制、整合或成本嗎？ |
| 開源 | 是否已有免費、可自架且足夠好的方案？ |
| 平台/bundle | Google、Microsoft、OpenAI、Adobe、Shopify 等平台是否能吸收功能？ |
| Enterprise | 大型 suite 是否透過採購、整合與信任勝出？ |
| 區域解法 | 不同國家是否因通路、法規或行為形成不同方案？ |
| 不作為 | 客戶是否能忍受問題？這通常是最強競品。 |

對重要替代方案比較：目標客群、核心工作、機制、定價單位、導入摩擦、distribution、信任、切換成本、弱點與可核實證據。

尋找 wedge 時回答：

- 哪個狹窄情境被現有方案過度服務或服務不足？
- 新產品在哪一個可量化結果上至少顯著更好，而非只是介面更漂亮？
- 優勢是否會隨 incumbents 複製功能而消失？
- 從 wedge 擴張後是否仍有一致的資料、工作流或 distribution 優勢？

## 3. Commercialization

固定分析下列九項：

1. **Customer**：ICP、使用者、champion、決策者、付款者與阻擋者。
2. **Pain**：痛點的量化成本、風險與急迫性。
3. **Frequency**：使用頻率、購買頻率與價值實現頻率。
4. **Willingness to Pay**：現有預算、替代成本、可衡量 ROI 與付款承諾。
5. **Switching Cost**：資料遷移、流程改變、培訓、整合、政治與合規。
6. **Distribution**：如何在需要發生的時刻接觸客戶；是否有 unfair access？
7. **Acquisition**：銷售週期、CAC 假說、self-serve 或 sales-led，以及早期通路是否可重複。
8. **Retention**：價值是否持續、是否嵌入工作流、資料或協作；問題消失後會不會取消？
9. **Expansion**：seat、usage、data、workflow、department、geography 或 marketplace 的擴張路徑。

定價分析不要只建議價格數字。先定義價值度量與收費單位：seat、usage、outcome、asset、location、workspace、revenue managed 等。檢查該單位是否與客戶價值同步、可預測、難以規避且不抑制核心使用。

商業模式紅旗：

- 使用者很痛，但沒有預算權；付費者感受不到價值。
- 問題頻繁但每次價值太小，無法支撐 acquisition。
- 只在一次性專案有價值，卻採訂閱模式。
- 需要大量客製服務才能交付標準 SaaS 承諾。
- 毛利取決於不可控 API 成本、人工審核或資料授權。
- 易於試用但沒有持續使用的自然觸發。

## 4. Second-order Thinking

不要只問產品推出後會怎樣；問成功本身會改變什麼。

### 必測情境

- **成功反應**：若快速成長，三年後最危險的競爭者是誰？它擁有什麼 distribution、data 或 bundle 優勢？
- **平台進入**：若 Google、Microsoft、OpenAI 或核心平台免費內建 80% 功能，剩餘價值是什麼？
- **免費化**：若開源或競品把價格降到零，客戶仍為什麼付費？
- **API 被封**：若 API、爬蟲、extension policy 或資料授權消失，產品是否仍可運作？
- **成本降至 1%**：若模型、運算或資料成本暴跌，優勢擴大還是被商品化？
- **成本上升 10 倍**：毛利、價格與產品體驗是否崩潰？
- **規則改變**：隱私、版權、SEO、廣告、AI disclosure 或產業法規如何改變需求與責任？
- **使用者適應**：客戶學會新行為後，產品是更重要還是可以被移除？
- **反向選擇**：產品是否吸引最難服務、最不願付費或流失最高的客戶？
- **Goodhart 效應**：指標成為目標後是否能被操弄，並傷害真正結果？

對每個高影響情境寫出：觸發、時間範圍、領先指標、影響、可逆性與緩解方式。

## 5. VC / Adversarial Partner

採用嚴格投資委員會視角，但不要模仿特定真實人物或假裝代表基金。回答：

- 這是 feature、product、business，還是能形成大型公司的起點？
- 10 倍優勢具體落在哪個客戶結果？是否可測量？
- 為什麼現有公司尚未做、做不好，或不願做？
- 若產品功能可在六個月內複製，還剩下什麼？
- distribution 是計畫、已驗證機制，還是希望？
- 市場規模是 top-down 報告，還是可由客戶數 × 合理 ACV bottom-up 推導？
- 早期 wedge 是否能通往足夠大的相鄰市場？
- 成長需要與收入等比例增加的人力嗎？
- 哪個里程碑能最大幅度降低需求、通路或技術風險？
- 為何是現在、為何是這個團隊？若團隊資料未知就標示未知。

### 護城河測試

- **Network effect**：每增加一名使用者，是否直接提高其他使用者的價值？只說「有更多使用者」不算。
- **Data flywheel**：使用是否產生獨特、合法、可用的資料？資料是否實際改善產品？改善是否帶來更多使用？競品能否取得等價資料？四項皆需成立。
- **Switching cost**：離開是否造成資料、工作流、協作、合規或經濟損失？單純不想學新 UI 很弱。
- **Scale economy**：規模是否降低單位成本或提高品質，且新進者難以複製？
- **Brand/trust**：在高風險決策中是否真正降低採購阻力？
- **Distribution advantage**：是否擁有專屬社群、嵌入式通路、合作夥伴或產品迴圈？付費廣告不是護城河。
- **Workflow ownership**：是否成為 system of record、approval layer 或每日關鍵流程？

## 6. Strategy Quality

### JTBD 與需求側思考

描述顧客從舊解法切換的力量：現況的 push、新解法的 pull、新解法的 anxiety、舊習慣的 inertia。若 pull 只來自新奇，切換很可能不發生。

### Blue Ocean Strategy

用 ERRC 檢查價值創新：

- Eliminate：產業慣例中哪些客戶不需要？
- Reduce：哪些要素被過度提供？
- Raise：哪些關鍵結果應高於標準？
- Create：哪些新價值能吸引非顧客？

「沒有競品」不是藍海。必須同時解釋新需求、成本結構及競爭要素如何改寫。

### Good Strategy / Bad Strategy

真正策略必須包含：

1. Diagnosis：明確指出最關鍵的障礙或結構。
2. Guiding policy：選擇如何集中資源克服障礙。
3. Coherent actions：一組互相強化的行動。

若內容只是願景、目標、口號、成長數字或互相衝突的待辦清單，標記為壞策略。

### Diffusion of Innovations 與 Crossing the Chasm

檢查 relative advantage、compatibility、complexity、trialability、observability。再區分早期採用者與務實主流客群：

- 誰有迫切 use case，願意忍受不完整產品？
- 主流客戶需要哪些完整產品、整合、證明、服務與風險保障？
- 是否有一個可主導的 beachhead，而不是同時服務所有產業？
- 早期採用者喜歡的客製與新奇，是否反而阻礙標準化？

## 7. 致命假設與整合判讀

把假設分為需求、商業、通路、產品/技術、平台/法規與護城河。使用兩個維度排序：若錯誤對計畫的破壞程度，以及目前證據有多弱。

致命假設具有三個特徵：一旦錯誤會使模式失效、目前主要靠推測、且能用較低成本在建造完整產品前測試。

不要讓總分沖淡 hard constraint。例如 API 合法性、單位經濟或付款者不存在，即使其他項目很強仍可導致「停止」或「先驗證」。
